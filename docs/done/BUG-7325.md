# BUG-7325 — Seed the worker's `.wixsharp` directory at build time

**Status:** DONE
**Branch:** `bugfix/bug-7325-seed-wixsharp-dir`
**Plan:** `docs/plan/BUG-7325.md`
**Run:** vibe/2026-10-22-wixsharp-dir-compression

## Summary

WixSharp packages the managed UI's custom action from a `.wixsharp` folder beside its client assembly
(`Enigma.Msi.Worker.exe`), and creates and fills it on the first MSI build. Nothing created it earlier, so
it was missing from every build output, publish and MSI. An app installed under Program Files could
therefore never create it, and every build failed with
`UnauthorizedAccessException: Access to the path '…\worker\.wixsharp' is denied.`

The worker project now seeds the folder itself. A new `SeedWixSharpBuildDir` target copies exactly what
WixSharp's first use writes into `bin/<cfg>/net472/.wixsharp/`, and `Copy` keeps last-write times. WixSharp
treats a copy with its original's length and a last-write time no older than the original's as current,
so it skips every file and writes nothing at run time. `CopyWorkerOutput.targets`' existing recursive glob
carries the folder into each host's `worker/` (build and publish), and from the publish into the MSI. No
host changed. A worker-suite drift guard runs WixSharp's own location rule and freshness predicate against
the real output.

## Decisions taken at build time

| Question | Chosen | Why | Alternatives rejected |
|---|---|---|---|
| Hook point | `AfterTargets="CopyFilesToOutputDirectory"` | Every copy-local reference is in `$(OutDir)` by then. It also runs before `IncrementalClean`, so the `FileWrites` entries reach `FileListAbsolute.txt` and `dotnet clean` removes the copies (verified). | `AfterTargets="Build"` (after `IncrementalClean`, so Clean would not know the files) |
| Missing-source check | One batched `<Error>` over the item list | One message per missing file, each naming it | A single `Exists` over a joined list (says *that* something is missing, not *what*) |
| How the test finds the worker output | An `AssemblyMetadata` attribute stamped by the test csproj | MSBuild knows the configuration and the contract path; the test does not have to guess either from its own location | Walking up from `AppContext.BaseDirectory` and inferring the configuration from folder names |
| WixSharp's cached build-dir field | Cleared for the read and restored afterwards, along with `Compiler.ClientAssembly` | `Utils.WixsharpBuildDir` caches its first value process-wide; the test must read *this* client assembly's folder and leave no global state behind | Leaving the cache set (it would leak a worker-output path into any later WixSharp call in the test process) |
| Folder existence asserted before resolving | Yes | Resolving the folder creates it when it is missing; an empty folder made by the test must not pass for a seeded one | Resolving first |

- **Follow-up:** a host that overrides `EnigmaMsiWorkerSourceDir` with a worker output from elsewhere gets a

  today.
- **Workaround for existing installs (1.0.0–1.4.0),** stated in the release notes: run the app once as
  administrator and build one MSI to create the folder. The proper fix is the next release's MSI.
- **Footprint:** the seed adds about 1.8 MB (six files) to the worker folder and the installed app. That is
  exactly what first use would have created anyway.
- **Side effect worth knowing:** two builds starting at once on a fresh install no longer race to create
  and fill the folder.
- **CRLF:** no line-ending inconsistency observed in the touched files.

**The tests detect what they guard (negative checks, run by hand and then rebuilt):**

**The bug, reproduced before the fix:** the plan's baseline worker, write-denied (`icacls /deny
<user>:(OI)(CI)(WD,AD)`, i.e. create files/sub-folders), failed:

```
The build failed with 1 error(s):
  UnauthorizedAccessException: Access to the path '…\run2\worker\.wixsharp' is denied.
```

**The fix, end to end:**
1. `dotnet publish src/Enigma.Msi.Desktop -c Release -r win-x64 --self-contained false` →
   `publish/worker/.wixsharp/` holds the six files.
2. The desktop app's worker built an MSI from that publish folder, from a copy of the 1.4.0 profile with
   absolute paths and `compression: None`: exit 0, 5 s, 49.5 MB.
3. `msiexec /a … /qn TARGETDIR=…` extracted it. `PFiles\Enigma.Msi\worker\.wixsharp\` is present, and each of
   its six files has the same length and last-write time as its original in `worker\` (cabinet-rounded,
   equal on both sides).
4. The extracted worker was write-denied (`WD,AD`; a probe file write was refused) and ran a build: **exit 0,
   MSI written**, and `.wixsharp` unchanged (names, lengths, timestamps compared before and after).
5. The deny ACEs were removed afterwards.

An actual per-machine install, launch and uninstall stays the maintainer's step, per `docs/RELEASE.md`.
