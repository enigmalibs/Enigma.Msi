# FEATURE-5F00-PHASE04 — Desktop app release prep (MSI profile & dogfood build) (DONE)

## Summary

The desktop app is now releasable: it declares `<Version>1.0.0</Version>`, it has an application icon,
and `msiProfiles/Enigma.Msi.Desktop.1.0.0.msipkg.json` describes its installer in the library's own
`.msipkg.json` format. The profile was **built** with the project's own worker — the dogfood loop closes:
`Enigma.Msi` builds the installer for the app that drives `Enigma.Msi`. This is also FEATURE-43A9's
outstanding manual acceptance step (end-to-end MSI generation), performed for the first time.

Three things did not go the way the plan assumed, all confirmed with the maintainer before acting:

- **The plan's `releasePath` would have shipped a 156 MB installer.** `bin/Release/net10.0` is a *build*
  output: it carries `runtimes/` for Linux, macOS and browser — 552 MB of Skia/HarfBuzz natives a Windows
  installer must never contain. Measured, not assumed (table under *Payload*). The profile now packages a
  RID-specific **publish** output, which took the MSI from 156 MB to **17.2 MB**.
- **The icon gate was closed by generating the icon**, on the maintainer's instruction, rather than by
  sourcing artwork or shipping without one.
- **Making the publish payload work needed a build fix.** `dotnet publish -r win-x64` flowed its
  `RuntimeIdentifier` into the `net472` worker, moving the worker's output to a RID-suffixed folder that
  neither `build/CopyWorkerOutput.targets` nor the library's pack target globs.

## Payload — why `releasePath` deviates from the plan

Measured on this machine, all four variants built end to end:

| `install.releasePath` | Installed | MSI |
|---|---|---|
| `bin\Release\net10.0` — as the plan writes it | 580 MB | 156 MB |
| `…\net10.0\win-x64\publish` (framework-dependent) | 150 MB | 36 MB |
| **…same, native `.pdb` trimmed — chosen** | **44 MB** | **17.2 MB** |
| …self-contained | 226 MB | ~55 MB (not built) |

The build output's bulk is `runtimes/` (552 MB): Skia and HarfBuzz natives for every platform Avalonia
supports. A RID-specific publish drops all but `win-x64`. What remains is dominated by the *debug symbols*
of those natives — `libSkiaSharp.pdb` is 80 MB and `libHarfBuzzSharp.pdb` 20 MB — which arrive as ordinary
native assets and so land in the publish output. `TrimNativeSymbolsFromPublish` removes only those:

```xml
<Target Name="TrimNativeSymbolsFromPublish" AfterTargets="ComputeResolvedFilesToPublishList">
  <ItemGroup>
    <_EnigmaNativeSymbol Include="@(ResolvedFileToPublish)"
                         Condition="'%(ResolvedFileToPublish.AssetType)' == 'native' AND '%(Extension)' == '.pdb'" />
    <ResolvedFileToPublish Remove="@(_EnigmaNativeSymbol)" />
  </ItemGroup>
</Target>
```

The `AssetType == 'native'` clause is what makes it safe: the four **managed** `.pdb` files (the app, both
faces of the library, the worker) are kept — they are ~120 KB in total and are what makes a support stack
trace readable. Verified by listing the publish tree afterwards.

**Consequence for the release, and for PHASE05:** the framework-dependent choice means the target machine
needs the .NET 10 runtime. That is the deliberate trade for a 17 MB installer; `--self-contained true`
remains a one-flag change if the prerequisite ever proves to be friction.

## The RuntimeIdentifier leak (and the route that does *not* work)

`dotnet publish -r win-x64` passes `RuntimeIdentifier` as a global property, which flows down the
build-order `ProjectReference` into the `net472` worker. The worker then builds to
`bin/Release/net472/win-x64/`, while both `build/CopyWorkerOutput.targets` and the library's
`PackEnigmaMsiWorkerPayload` target glob `bin/$(Configuration)/net472/`. On a clean tree that fails with
*"No worker files were found"*; on a dirty tree it silently copies a **stale** worker, which is worse.

The obvious fix — adding `RuntimeIdentifier` to the reference's `UndefineProperties` — was tried and
**fails**, in both variants (`;RuntimeIdentifier` and `;RuntimeIdentifier;SelfContained`):

```
error NETSDK1047: Assets file '…\Enigma.Msi.Worker\obj\project.assets.json'
doesn't have a target for 'net472/win-x86'.
```

NuGet's restore graph walk does not honour `UndefineProperties`, so restore resolved `win-x64` while the
build, with the property undefined, fell back to the worker's *own* inferred RID — which for a .NET
Framework exe is `win-x86` (confirmed directly: `dotnet msbuild … -getProperty:RuntimeIdentifier` on the
worker prints `win-x86`). Restore and build disagreed, and the assets file had no `net472/win-x86` target.

The fix therefore sits in the worker itself: `<AppendRuntimeIdentifierToOutputPath>false</…>`. The RID
still flows down and restore and build stay consistent — only the output path is pinned. That is the
right home for it regardless: `bin/$(Configuration)/net472/` is a contract two other files depend on, so
the worker should guarantee it rather than every host defending against it. Verified from a clean worker
`bin/` + `obj/`.

## Icon

No `.ico` existed and none was supplied; on instruction it was **generated** rather than deferred. The
generator is a scratchpad console app with no dependencies: it evaluates a rounded-square plate and three
convex polygons per sample point at 8× supersampling, resolves coverage in premultiplied alpha, then
writes the `.ico` container itself — `BITMAPINFOHEADER` + bottom-up BGRA + a zeroed AND mask below 128 px,
and hand-rolled PNG (IHDR/IDAT/IEND, `ZLibStream`, own CRC-32) at 128 and 256. The result was extracted
back out of the container and inspected as an image before being accepted.

Wired through all three places it has to appear, each verified in the artifact rather than assumed:

| Where | How | Verified |
|---|---|---|
| The `.exe` | `<ApplicationIcon>` | `ExtractAssociatedIcon` on the published exe returns an icon |
| Add/Remove Programs | `controlPanel.productIcon` | MSI `Property` table: `ARPPRODUCTICON = app_icon.ico` |
| Both shortcuts | `shortcuts[].iconPath` | MSI `Shortcut.Icon_` = `IconFile1_appicon.ico` on both rows |
| The app window | `Icon="/Assets/appicon.ico"` | Compiles under `AVLN`-as-error; picked up by the existing `<AvaloniaResource Include="Assets/**" />` |

`.gitattributes` already declares `*.ico binary`, so nothing had to change there.

## Deviations & follow-ups

- **`releasePath` deviates from the plan's literal value**, with the maintainer's decision, for the reason
  measured above. The plan's `PHASE04` and `PHASE05` sections were updated to record it.
- **The dogfood MSI was built, not installed.** Installing a per-machine MSI requires elevation and
  modifies the maintainer's machine, so that half stays theirs. To complete it, from the repository root:
  ```
  msiexec /i artifacts\Enigma.Msi.Desktop.msi
  msiexec /x artifacts\Enigma.Msi.Desktop.msi
  ```
  What was verified instead, by reading the MSI's own tables (no install): 102 `File` rows including
  `Enigma.Msi.Worker.exe` and its `.config`; two `Shortcut` rows both named `Enigma.Msi.Desktop.lnk`, both
  carrying the icon; `ProductName` `Enigma.Msi.Desktop`; `Manufacturer` `Josué Clément` with its accents
  intact; `ProductVersion` `1.0.0`; `UpgradeCode` as contracted; `ALLUSERS = 1`, i.e. `PerMachine` really
  did map through.
- **The profile carries `controlPanel.productIcon` and nothing else of `ControlPanelInfo`.** The plan's
  field list names only the icon, so `comments`, `contact`, `helpLink` and `urlInfoAbout` were left unset
  rather than invented. *Follow-up:* `helpLink`/`urlInfoAbout` pointing at
  `https://github.com/enigmalibs/Enigma.Msi` would be a genuine improvement to the Control Panel entry —
  a one-line profile edit whenever wanted.
- **`ui` is left unset**, so the build applies `UiSettings.CreateDefault()` (WixUI_InstallDir;
  Welcome/InstallDir/Progress/Exit and Welcome/MaintenanceType/Progress/Exit). Deliberate: the plan does
  not list `ui`, and the default is the intended sequence.
- **`install.installPath` is `%ProgramFiles%\Enigma.Msi`** exactly as planned, though the product is
  `Enigma.Msi.Desktop`. Left as decided — flagged only because a second shipped artifact under the same
  folder would collide.
- **The library's pack target has the same RID-leak exposure** that was just fixed for the app:
  `PackEnigmaMsiWorkerPayload` globs `bin/$(Configuration)/net472/` too. It is now protected by the
  worker-side `AppendRuntimeIdentifierToOutputPath`, so nothing is broken — noting it so the connection
  isn't lost: that property is load-bearing for packing as well as for publishing.
- **`.msipkg.json` non-ASCII escaping.** `MsiPackageJson.Options` uses the default `JavaScriptEncoder`, so
  any accented character in a profile is written as `\uXXXX`. Round-trips perfectly and is what the
  desktop app already writes; but for a format explicitly described as hand-editable,
  `JavaScriptEncoder.UnsafeRelaxedJsonEscaping` would read far better. *Follow-up (library change, own
  work item — it alters every profile the library writes).*
- **Follow-up for PHASE05:** the runbook must state that the app-MSI step runs **from the repository
  root** and that `dotnet publish -r win-x64 --self-contained false` is a hard prerequisite of it — the
  profile packages the publish directory, and a stale or missing publish silently ships the wrong payload.
  Added to the plan's PHASE05 step 1.
- **Line endings:** no CRLF churn. The generated profile is written LF-only (the generator normalizes
  before writing, since `Utf8JsonWriter` indents with `Environment.NewLine` on Windows); `appicon.ico` is
  covered by the existing `*.ico binary` rule.
