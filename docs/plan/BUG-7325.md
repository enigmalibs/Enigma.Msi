# BUG-7325 — Seed the worker's `.wixsharp` directory at build time

**Status:** TODO
**Type:** BUG (single-phase)
**Branch:** `bugfix/bug-7325-seed-wixsharp-dir` — cut from the run-branch tip.
**Run:** vibe/2026-10-22-wixsharp-dir-compression

## Objective

An installed Enigma.Msi.Desktop must be able to build an MSI **from a worker folder it cannot write to** —
which is what `%ProgramFiles%\Enigma.Msi\worker\` is for a standard user.

Today the worker's first MSI build creates `worker\.wixsharp\` and copies five assemblies into it. Nothing
creates that folder at build time, so a freshly built or published app — and therefore the MSI made from
it — does not contain it, and the first build after an install under Program Files fails:

```
The build failed with 1 error(s):
  UnauthorizedAccessException: Access to the path '…\worker\.wixsharp' is denied.
```

Fix: **make `.wixsharp\` part of the worker's own build output**, seeded with exactly what WixSharp would
put there, so every host's `worker\` folder — build output, publish output and the MSI built from it —
already carries it, and WixSharp writes nothing at run time.

## Context & constraints

Read from the repository and verified on Windows at planning time (2026-10-22):

- **What WixSharp does** (WixSharp_wix4 **2.14.1**, decompiled): `Utils.WixsharpBuildDir` is
  `Path.GetDirectoryName(Compiler.ClientAssembly)` + `.wixsharp`, created with `Directory.CreateDirectory`
  (a no-op when it exists). `Compiler.PackageManagedAsm` — run for the `ManagedUI` embedded UI every
  `MsiProjectFactory` project carries — calls `Utils.IsolateAsm` on the client assembly and on every
  required assembly. `IsolateAsm` copies a file into the folder **unless** `IsUpToDateCopyOf(dest, src)`
  holds: same length and `src.LastWriteTimeUtc <= dest.LastWriteTimeUtc`. When it does copy the client
  assembly, it copies its `.pdb` alongside.
- **What lands there, observed** — a real `Enigma.Msi.Worker.exe build` against WiX 7.0.0 from a fresh
  copy of `src/Enigma.Msi.Worker/bin/Release/net472/` produced `.wixsharp\` holding
  `Enigma.Msi.Worker.exe`, `Enigma.Msi.Worker.pdb`, `WixSharp.dll`, `WixSharp.UI.dll`,
  `WixToolset.Dtf.WindowsInstaller.dll`, `WixToolset.Mba.Core.dll` — every copy carrying its source's
  last-write time. All six sources sit in the worker's own output directory.
- **The bug, reproduced** — the same build run from a worker folder whose ACL denies the current user
  `WD,AD` (create files / create sub-directories, what Program Files denies a standard user) fails with the
  `UnauthorizedAccessException` above (exit 1). With a pre-seeded `.wixsharp\` it succeeds (exit 0).
- **The deployment path** — `build/CopyWorkerOutput.targets` copies `$(EnigmaMsiWorkerSourceDir)**/*`
  (default: the worker's `bin/$(Configuration)/net472/`) into each host's `$(OutDir)worker/` and
  `$(PublishDir)worker/` with `%(RecursiveDir)`, and the MSI packages the publish folder recursively
  (`MsiProjectFactory`'s `Files(… *.*)`). A folder inside the worker's output therefore reaches the MSI with
  no change to the hosts.
- **The library suite's stub worker** is deployed by the same targets file from another source directory;
  it must stay unaffected.
- Zero-warning builds, MTP-native tests (`dotnet test --solution Enigma.Msi.slnx -c Release`), CPM, one type
  per file, explicit usings.

## Decisions

1. **Seed in the worker project, not in the hosts.** `.wixsharp` is a property of the worker — WixSharp
   puts it beside its client assembly — so the worker's build output is where it belongs; the existing glob
   carries it everywhere else.
2. **An MSBuild target, not a `PostBuildEvent`.** Cross-platform, incremental (`SkipUnchangedFiles`),
   and registered in `FileWrites` so `dotnet clean` removes it. `Copy` preserves last-write times, which
   is precisely what `IsUpToDateCopyOf` needs.
3. **Seed what first use produces:** the five assemblies, plus the worker's `.pdb` when it exists.
4. **A missing seed source fails the build**, naming the file — a WixSharp upgrade that renames or drops
   an assembly must fail loudly.
5. **A worker-suite drift guard** runs WixSharp's own location rule and freshness predicate against the
   worker's real build output.

## Steps

1. `src/Enigma.Msi.Worker/Enigma.Msi.Worker.csproj` — add the target `SeedWixSharpBuildDir`
   (`AfterTargets="CopyFilesToOutputDirectory"`):
   - collect the five assemblies from `$(OutDir)` (the exe as `$(TargetFileName)`), plus
     `$(OutDir)$(TargetName).pdb` when it exists;
   - `<Error>` for any missing source, naming it and pointing at the WixSharp version;
   - `Copy` into `$(OutDir).wixsharp/` with `SkipUnchangedFiles="true"`, its `DestinationFiles` added to
     `FileWrites`;
   - a comment explaining *why* (WixSharp's first-use write, the read-only install, the freshness rule).
2. `build/CopyWorkerOutput.targets` — a comment only: the `**/*` glob deliberately includes the worker's
   `.wixsharp/` sub-folder, so it must never be narrowed to the top level.
3. `tests/Enigma.Msi.Worker.UnitTests/Enigma.Msi.Worker.UnitTests.csproj` — stamp the worker's output
   directory (`$(MSBuildThisFileDirectory)../../src/Enigma.Msi.Worker/bin/$(Configuration)/net472/`, the
   same path `CopyWorkerOutput.targets` defaults to) as an `AssemblyMetadata` attribute.
4. `tests/Enigma.Msi.Worker.UnitTests/WixSharpBuildDirTests.cs` — the drift guard:
   - WixSharp resolves its build directory to `<worker output>/.wixsharp` for the worker exe as client
     assembly (via the internal `Utils.WixsharpBuildDir`, with `Compiler.ClientAssembly` restored after);
   - each of the five assemblies has a copy there that WixSharp's own `IsUpToDateCopyOf` accepts as up to
     date;
   - a missing internal member fails with a message saying what to re-verify.
5. Docs: a `CLAUDE.md` paragraph beside the `bin/$(Configuration)/net472/` contract, plus a short
   build-state entry; a `RELEASENOTES.md` `## (unreleased)` section with this fix.
6. Manual end-to-end check (Windows, WiX CLI): build and publish the desktop app, confirm
   `worker/.wixsharp/` in both outputs, build an MSI from the publish folder, extract it with an
   administrative install and run a build from the extracted, write-denied worker.

## Acceptance criteria

- [ ] After `dotnet build Enigma.Msi.slnx -c Release`, `src/Enigma.Msi.Worker/bin/Release/net472/.wixsharp/`
      holds the five assemblies and `Enigma.Msi.Worker.pdb`, each with its source's length and last-write
      time.
- [ ] The desktop app's `bin/Release/net10.0/worker/.wixsharp/` and its `win-x64` publish
      `…/publish/worker/.wixsharp/` hold the same six files.
- [ ] A rebuild with no change copies nothing again (incremental), and `dotnet clean` removes the folder.
- [ ] A seed source missing from the output fails the worker build with an error naming it (verified by
      temporarily listing a file name the output does not contain).
- [ ] The new worker-suite tests pass; the whole suite passes; the build is warning-free.
- [ ] Manual: an MSI built from the publish folder contains `worker\.wixsharp\`, and a worker extracted from
      it builds an MSI from a folder the user cannot create files in.
- [ ] The library suite's `stub-worker` deployment is unchanged.
